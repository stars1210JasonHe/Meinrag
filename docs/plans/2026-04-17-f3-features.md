## F3.1 — Document Search (sidebar)

### Current state
- `DashboardPage.jsx:398-405` has a **top-bar search** that filters the dashboard doc list by substring match on filename/collection. No debounce (filters on every keystroke, fine for small N).
- `AppLayout.jsx` (main nav sidebar) has **no search**.

### Roadmap says
"FAISS search upgrade (vector search + debounce)"

### Three scope options — pick one:

| Option | Effort | What you get |
|---|---|---|
| **A. Polish existing** | ~30min | Add debounce (300ms) + clear button + "X results" counter to existing dashboard search. Keep substring match. |
| **B. Sidebar filter** | ~1h | Add a search input to the nav sidebar that filters docs across all pages. String-based. |
| **C. Semantic search** | ~4-6h | New `/documents/search?q=...` backend endpoint → embed query → FAISS against doc summary index → ranked results. Frontend replaces string filter with debounced async call. |

**Recommendation: A** — fastest user win without backend work. C is the roadmap's stated goal but adds significant backend complexity for a document list that's probably <50 docs per user. If you have 1000+ docs, C becomes worth it.

## F3.2 — Internationalization (i18n)

### Current state
- No i18n library. All strings hardcoded in JSX (~150+ strings across pages/components).
- `package.json` has no i18n deps.

### Three scope options — pick one:

| Option | Effort | What you get |
|---|---|---|
| **A. Skip for now** | 0 | Defer until you actually need a second language. |
| **B. Minimal setup** | ~2h | Add `react-i18next` + `i18next`. Extract ~30 high-value strings (nav, buttons, empty states). Add EN + one other language (pick: 中文 / Deutsch / Français). Language switcher in header. |
| **C. Full coverage** | ~6-8h | Extract all ~150 strings. 2-3 languages. Lazy-load locale files. Proper plural/date formatting. |

**Recommendation: A or B** — i18n is a "turn it on when you need it" feature. Option A saves the work. Option B is worth it if you want to demo multi-language support or actually plan to use it soon.

### New dependency alert
`react-i18next` is a new API I haven't used here before. User rule: **always ask before using any new/different API**. Please confirm library choice.

## F3.3 — Dark/Light Mode

### Current state
- Dark mode only. All colors inline HSL (e.g. `backgroundColor: 'hsl(222 47% 12%)'`) — hardcoded throughout all components.
- No theme context, no CSS custom properties, no Tailwind `dark:` classes.
- `index.css` defines some CSS vars but they're not referenced by inline styles.

### Three scope options — pick one:

| Option | Effort | What you get |
|---|---|---|
| **A. Skip for now** | 0 | Keep dark-only. Most RAG apps / dev tools are dark. |
| **B. Quick toggle** | ~2h | Light theme CSS vars in `:root[data-theme=light]`. Keep inline HSL for ~80% of styling (they override the root vars). Only major surfaces (bg, text, borders) get themed. Toggle button in header. Result: works but feels incomplete because many inline colors stay dark. |
| **C. Proper refactor** | ~4-6h | Refactor all inline HSL colors to CSS variables. Two full palettes (dark + light). Theme context + localStorage + system-preference detection + toggle. Done right. |

**Recommendation: A or C, not B** — option B produces a half-broken-looking app. Either skip or do it properly.
